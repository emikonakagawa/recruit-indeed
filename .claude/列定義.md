# 列定義（全列 A〜BR）

職種テンプレート（`テンプレート/テンプレート（職種）.xlsx`）の `求人入力シート` 1 行目ヘッダーに対応する、全列の分類・入力規則です。会社・職種をまたぐ共通リファレンスとして使います。

## 注釈タグの意味（テンプレート内のプレースホルダ）

| タグ | 意味 | 値の決め方 |
| --- | --- | --- |
| `【AI生成】` | 毎回スキルが生成する変動値 | 該当職種の `briefs/<職種>.md` に沿って生成 |
| `【会社毎】` | 会社固有の固定値 | `companies/<会社>/設定.md` から転記 |
| `【勤務地毎】` | 勤務地で決まる値 | `設定.md` の勤務地候補から選定 |
| `【会社・勤務地毎】` | 会社×勤務地で決まる値 | `設定.md`（東京/名古屋で別値） |
| `【内容固定／表現はAI生成】` | 内容は固定・言い回しは毎回変える | `設定.md` の素材を毎回言い換え |
| （注釈なし） | そのまま使う固定値 | テンプレートの値をそのまま |

**優先順位**: 職種テンプレートの固定値が既定。同じ列を `設定.md` が指定していれば **会社別設定が優先（上書き）**。

## タグ（BE/BF/BG）の入れ方に関する注意

媒体上タグ列は BE/BF/BG の 3 列に分かれていますが、過去の運用には 2 通りの書き方が混在しています。

- エンジニア系（UPBUILD）: `BE=在宅OK`, `BF=交通費支給`, `BG=昇給・昇格あり`（1 セルに 1 タグ）
- iRup（エンジニア・ITコンサルタント）: `BE=交通費支給`, `BF=昇給・昇格あり`, `BG=在宅OK`（2026-07-20 にユーザー指示で `在宅OK` を削除したが、2026-08-20 にユーザー指示で BG に復活）
- クリエイティブ系（Xedge 実績）: `BE=交通費支給`（BF/BG 空欄。2026-07-02 にユーザー指示で `在宅OK` を削除）

会社・職種ごとの正しい書き方は `companies/<会社>/設定.md` に明記してあるので、それに従う。

### Indeed タグの許容値（完全一致）

BE/BF/BG に入れられるタグ文字列は以下のみ。**他の表記は Indeed のアップロード検証で弾かれる**。

- `社員登用あり`
- `昇給・昇格あり`
- `残業なし`
- `週1日からOK`
- `週2・3日からOK`
- `シフト自由`
- `交通費支給`
- `即日勤務OK`
- `駅近5分以内`
- `フルリモート`
- `在宅OK`

過去に弾かれた値（**使ってはいけない**）:
- `在宅あり` → `在宅OK`（または `フルリモート`）に置換
- `昇給あり` → `昇給・昇格あり` に置換

旧テンプレ／旧設定にこれらの弾かれる値が残っているが、xlsx 生成時に **必ず許容値に書き換える**。

**既知の落とし穴（2026-08-10 UPBUILD 実送信で確認）**: `テンプレート（エンジニア）.xlsx` の **2 行目 BG セルに旧残存値 `昇給あり` が入っている**。この値は `【…】` 形式の注釈タグではないため、下記「テンプレ注釈の掃除」の `【…】` 検出ロジックでは空欄化されない。BE/BF だけを明示的に書き込み BG を触らずに保存すると、2 行目に限り `昇給あり` が残ってアップロード検証エラーになる（実際に発生した事例）。**BE/BF/BG は 3 列とも毎回明示的に値を設定する（使わない列は `None` を代入する）**ことで回避する。

## AD 列「試用期間（期間の単位）」の許容値

Indeed の許容値は **`日間` / `週間` / `か月`** の 3 つのみ。

- 旧テンプレに `ヶ月`（小書きの「ヶ」）が入っているが、これは Indeed に弾かれる。
- 正しくは `か月`（ひらがな「か」）。xlsx 生成時に必ず置換する。

## F 列（郵便番号）の必須注意

F 列は **文字列として 7 桁**で書き込む（例: `1500043`）。数値として書くと `1500043.0` のように float 化したり先頭ゼロが消えるため、必ず文字列で扱う。

## テンプレ注釈の掃除（build 時・全社共通）

職種テンプレの **2 行目**には各列に `【AI生成】` `【会社毎】` `【勤務地毎】` `【内容固定／表現はAI生成】` 等のプレースホルダ注釈が入っている。値を書き込まない列（例: **I=建物名・階数、BR=ユーザー指定ID** など）はこの注釈が残り、Indeed 一括アップロードで弾かれる（BR は 34 字で「30 字以下に」エラー）。

→ **xlsx 保存前に、データ行(2 行目以降)の全セルを走査し、`【` と `】` を含み注釈タグ語（`AI生成`/`会社毎`/`勤務地`/`内容固定`）を含むセルを `None` で空欄化する**。実装例:

```python
from openpyxl.utils import get_column_letter
TAGS = ('AI生成', '会社毎', '勤務地', '内容固定')
for r in range(2, last_row+1):
    for c in range(1, ws.max_column+1):
        v = ws.cell(r, c).value
        if isinstance(v, str) and '【' in v and '】' in v and any(t in v for t in TAGS):
            ws.cell(r, c).value = None
```

## C 列（職種名）の書式: 職種名のみ・簡潔で明確に

Indeed の審査では、職種名に仕事内容・研修・待遇・キャッチコピーなど「職種名以外の情報」が混ざると弾かれる（実際のエラー文: **「職種名: 職種名が不明確、または職種名以外の求人内容に記載すべき情報（仕事内容、雇用形態など）が含まれている可能性があります。職種名は簡潔で明確なものに修正してください。」**）。**C 列には職種名そのものだけを簡潔に書く**。

書式: **`【未経験可】<職種名>`**

- `【】` には **応募条件の短語のみ**（`未経験可` で統一）。
- `】` のあとは **職種名 1 語だけ**。研修期間・手当・賞与・「プロへ」「一気通貫」などの訴求や仕事内容は **入れない**（→ それらは E 列キャッチコピーや AT/AU 本文に書く）。
- **使わない**: `◆` `／` `｜` `▼` `●` `、` などで複数フレーズを並べる書き方（カテゴリー名内の `／` は除く・例: `インフラ／保守運用エンジニア`）。
- **会社・職種問わず統一**。20 字前後を目安に簡潔に。

職種別に C 列へ入れてよい職種名（1 つ選ぶ・クリエイティブ系）:

| 職種 | C 列の職種名（例） |
| --- | --- |
| Webデザイン | `Webデザイナー` |
| マーケティング | `SNSマーケター` / `Webマーケター` |
| 動画編集 | `動画クリエイター` / `動画編集クリエイター` |
| 出版 | `DTPデザイナー` / `出版デザイナー` / `グラフィックデザイナー` |

良い例:
- `【未経験可】Webデザイナー`
- `【未経験可】SNSマーケター`
- `【未経験可】動画クリエイター`
- `【未経験可】DTPデザイナー`

> 2026-07 Xedge パフォーマンス分析（実掲載データ）でも、この「`【未経験可】`＋職種名のみ」のシンプル形が最高 CTR 帯（13〜16%、全体平均10.7%を大きく上回る）を記録しており、職種名を修飾語で説明的に伸ばすタイトルより明確に効果が高いことが確認された。詳細・職種別の良い例／悪い例は各 `briefs/<職種>.md` 参照。
>
> 2026-08 iRup パフォーマンス分析（2026-07-04〜08-02・実掲載データ）でも同じ傾向が裏付けられた。業界名や案件名まで職種名に詰め込んだ**長く専門的すぎるタイトル**（例: 「銀行系基盤更改エンジニア（Linux）」CTR0.42%）や、**具体的な職種名を伴わない抽象的なキャッチのみのタイトル**（例: 「営業→ITキャリアアップ」CTR1.30%）は CTR が著しく低い。職種名はシンプルに保ち、キャリアチェンジのストーリーや訴求は E 列・本文側に回す（エンジニアの詳細は `エンジニア専門領域.md`「運用ルール」、iRup 固有の注意点は `companies/iRup/設定.md`「パフォーマンス実績に基づく優先順位」参照）。
>
> **2026-08-10 iRup パフォーマンス分析（2026-07-11〜08-09・実掲載データ）で追加確認**: 「訴求フレーズ無しの地方×専門職／汎用事務」タイトルは CTR が著しく低い（例: 「【横浜・片倉町】エンド直事務案件」CTR4.3%、「【テレコムセンター】モバイル管理業務アシスタント」CTR3.8%、「【岡山市】銀行系基盤更改Linuxエンジニア」CTR0.7%＝上記 2026-08 分析の傾向を再確認）。共通点は、地名・案件名などの**具体情報はあるが「未経験可」やキャリアの型となる訴求フレーズが無く**、ターゲットが狭いまま終わっている点。C 列は職種名のみのルールを維持しつつ、`【未経験可】` 等の訴求短語は必ず付け、キャリアの型（例: `｜〇〇なキャリア`）は E 列側で補う（iRup の高 CTR 実例は `briefs/ITコンサルタント.md`「パフォーマンス実績に基づく勝ちパターン」・`briefs/エンジニア.md`「E キャッチコピー」参照）。
>
> **2026-08-31 UPBUILD パフォーマンス分析（2026-08-01〜08-31・実掲載データ）**でも、タイトルは簡潔に保つほど応募につながりやすいという教訓が逆方向から確認された。`【】` タグを複数連結して属性を畳みかけるタイトル（例: 「【未経験可】【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析」）は CTR19.6% と高い一方 **CVR0%** で、クリックは集めても応募につながらなかった。C 列・タイトルはキーワード詰め込みで無理に CTR を稼がず職種名を簡潔に保つ（詳細は `エンジニア専門領域.md`「複数【】連結型」、`本文スタイル.md`「AT/AU/AV とタイトルの整合」、`companies/UPBUILD/設定.md`「追加分析（2026-08-31）」参照）。
>
> **2026-08-31 Xedge データセンター パフォーマンス分析（2026-08-01〜08-31・実掲載データ）**でも、抽象的な情緒コピーのみのタイトルは CTR が著しく低いという教訓が確認された（例: 「AI時代の舞台裏を支える｜設備エンジニア」CTR4.5%、「社会を止めないインフラを守る…ミッションクリティカルエンジニア」CTR5.3%）。一方、資格保有者を名指しし現状の不満に問いかける具体的なフック（例: 「電験三種を『活かせていない方へ』｜設備エンジニア」CTR14.4%）は高 CTR を維持している。C 列は職種名のみのルールを維持し、この種の具体フックは E 列側に寄せる（詳細は `briefs/データセンター.md`「E キャッチコピー」、`companies/Xedge/設定.md`「追加分析（2026-08-31）」参照）。
>
> **2026-08-31 iRup パフォーマンス分析（2026-08-01〜08-31・実掲載データ、コンサル＋エンジニア95件）**でも同じ教訓が確認された。「【未経験可】＋専門職種名＋ターゲット名指し」型（例: 「【未経験可】ITコンサルタント｜営業経験を武器にするキャリア」CTR27.1%・CVR25.0%、「【未経験可】外国籍｜クラウドエンジニア」CTR19.3%・CVR20.9%）が引き続き最強である一方、`【】` タグを複数連結して冗長になったタイトル（「【未経験可】【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析」CTR11.2%・応募0）は名指しがぼやけ相対的に弱い（詳細は `briefs/エンジニア.md`「E キャッチコピー」、`briefs/ITコンサルタント.md`「追加分析（2026-08-31）」、`companies/iRup/設定.md`「パフォーマンス実績の更新（2026-08-31）」参照）。

悪い例（審査で弾かれる）:
- `【未経験OK】研修1年でプロのWebデザイナーへ、推し活手当も`（研修・手当など職種名以外の情報が混入）
- `【未経験OK】未経験から半年でSNSマーケターへ、賞与年4回`（期間・賞与が混入）
- `【未経験OK】Webデザイナー◆研修1年・推し活手当あり`（◆ で区切っている）

> 研修・手当・賞与・**年収（金額の言及がなくても「年収を上げる」等の表現を含む）**などの報酬関連の訴求は、職種名から外して **E 列（求人キャッチコピー）や AT/AU 本文**に書く。「年収」を含む C 列タイトルは iRup の実績（2026-07-02「その営業力、ITで年収に変えませんか？」エンジニア募集）で「確認事項あり」警告の対象になっており、`研修`/`手当`/`賞与` と同様のリスクがある（詳細は `companies/iRup/設定.md`「C 列: iRup 専用の対人スキル訴求スタイル」候補プールの注記）。

### C 列職種名エラーの予防ルール（2026-07 iRup 非掲載分析で確認）

「職種名以外の情報」は研修・手当・賞与だけでなく、**残業時間・語学条件などの応募条件も含む**。`【】` 接頭タグの中に `未経験可` 以外の条件を詰め込むと、たとえ短い語でも「職種名以外の情報が含まれる」として非掲載になる（2026-07 iRup で実績あり）。

悪い例（非掲載になった実例）:
- `【未経験可/残業10時間未満】事務バックオフィス`（接頭タグに残業時間の条件が混入）
- `【中国語 歓迎】ITエンジニアサポート`（接頭タグに語学条件が混入。`【】` 内に `未経験可` 以外の条件を入れている点が問題）

良い例（許容ラインに寄せた修正）:
- `【未経験可】事務・バックオフィス`（残業条件は E 列・本文へ）
- `ITエンジニアサポート`（語学条件を外し職種名のみに。安全策）
- 属性訴求をタイトルに残したい場合は、`【】` 接頭タグを使わず **自然文でタイトル先頭に置く**（例: `中国語歓迎 ITエンジニアサポート` は括弧なしの自然文形式で掲載実績・高 CTR あり。詳細は `companies/iRup/設定.md`「属性限定型の候補プール」）。**`【〇〇歓迎】` のように接頭タグ化しない**のが分かれ目。

残業時間・語学条件・勤務地などの応募条件は、C 列ではなく **E 列（求人キャッチコピー）／本文（AT/AU/AV）** に書く。

> 事務・コールセンター・サポート系は現時点で専用テンプレート／ブリーフが無い（`briefs/` 未整備）。この種の職種を `draft-jobs` 経由で作る場合は、先に `briefs/` へ新設するか、既存テンプレートの C 列ルールに準拠させること（2026-07 時点の非掲載 4 件はいずれも xlsx を介さない直接投稿で、対応する xlsx 行は無し）。

### エンジニアは固定書式（別 SSoT）

エンジニア求人も同じく「職種名のみ・簡潔」の方針で、**固定書式 `【未経験可】フルリモートあり〇〇エンジニア`** を用いる。〇〇 に入るワード一覧・書式の細則・良い例／悪い例は **[`エンジニア専門領域.md`](./エンジニア専門領域.md)** が SSoT。iRup・UPBUILD 全社統一（Xedge はエンジニア求人を作らない）。

## 雇用形態エラーの予防ルール（J・AE/AF〜AS・BB、2026-07 iRup 非掲載分析で確認）

Indeed の審査は、**試用期間を含む初回契約時の実際の雇用形態と、記載内容（福利厚生等）が一致しているか**を確認する。不一致だと「雇用形態の記載に誤解を招く表現/不明瞭な点がある」「試用期間を含む初回契約時の実際の雇用形態と一致しているか」「当該雇用形態にのみ適用される福利厚生のみが記載されているか」という趣旨の確認事項で非掲載になる（2026-07 iRup の事務・コールセンター系求人 3 件で実績あり）。

- J（雇用形態）と AE（試用期間の労働条件）を必ず整合させる。**本プロジェクトの既定（J=`正社員`／AE=`同条件`）を使う限り、試用期間中も正社員と同条件のため通常は問題ない。**
- AE を `同条件` 以外にする場合は、AF〜AS（試用期間中の給与形態・固定残業代・労働時間等）を必ず埋め、試用期間中の実際の雇用形態・条件を明記する（空欄のままにしない）。
- BB（福利厚生）には、**その求人の実際の雇用形態（通常は正社員）にのみ適用される福利厚生だけ**を記載する。アルバイト・契約社員向けの制度を正社員求人に混在させたり、その逆をしたりしない。
- xlsx 生成フロー（`draft-jobs`）は J=`正社員`／AE=`同条件` を既定で使うため通常は再発しないが、**xlsx を介さない直接投稿でも本ルールを適用する**（2026-07 iRup の非掲載 4 件はすべて直接投稿）。

## 給与関連の固定ルール（M / N / BA）

会社・職種・勤務地に依存する給与関連は以下の固定ルールに従う（**会社問わず統一**。`設定.md` の給与レンジ記述よりこちらが優先）。

### M 給与（最低額）

| 勤務地 | 全職種共通 |
| --- | --- |
| 東京 | `250000` |
| 名古屋 | `230000` |

### N 給与（最高額）

| 勤務地 | エンジニア | エンジニア以外 |
| --- | --- | --- |
| 東京 | `600000` | 空欄 |
| 名古屋 | `500000` | 空欄 |

### BA 募集要項（給与の補足）の冒頭表記

冒頭はこの月給レンジ表記で固定。モデル年収・昇給賞与・各種手当などの補足はその下に職種ごとに続ける（エンジニアはモデル年収等を必ず添える、クリエイティブ系は省略可）。

| 勤務地 | エンジニア | エンジニア以外 |
| --- | --- | --- |
| 東京 | `月給：25万円〜60万円＋各種手当` | `月給：25万円〜　＋各種手当` |
| 名古屋 | `月給：23万円〜50万円＋各種手当` | `月給：23万円〜　＋各種手当` |

- エンジニア以外は `〜` の後ろに **全角スペース1つ** を入れて `＋各種手当` に続ける（最高額なしを明示）。
- N（数値）と BA の表記は整合（エンジニア以外は両方とも最高額なし）。

### N 列の例外（O=範囲で表示のとき）

上記「エンジニア以外は N 空欄」が既定だが、**O（給与の表示形式）＝`範囲で表示` を選ぶ場合、Indeed の一括アップロード検証は職種を問わず N を必須とする**（2026-07-02 iRup「ITコンサルタント」求人の実送信で確認済み。エンジニア以外でも N が空欄だと弾かれた）。エンジニア以外の職種で N を空欄にしたい場合は、O を `最低額を表示` にする（この組み合わせで N 空欄が通るかは未検証。次回確認时に本欄を更新すること）。N を入れる場合は、想定年収上限 ÷ 12 など根拠のある値を使い、BA の補足文と整合させる（例: iRup ITコンサルタントは N=580000、BA に「想定年収400万円〜700万円」と記載）。
