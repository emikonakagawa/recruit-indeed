# エンジニア専門領域・C列職種名一覧

エンジニア求人の **C 列（職種名）** は、Indeed の審査エラー（「職種名が不明確」「職種名以外の情報が含まれている」など）を避けるため、**以下の固定書式**で生成する。

## C 列の固定書式（エンジニアのみ）

```
【未経験可】フルリモートあり〇〇エンジニア
```

- **冒頭の `【未経験可】` と `フルリモートあり` は固定**。並べ替え・省略・別表現への変更は不可。
- `フルリモートあり`（`あり` を付ける）とし、**「フルリモート」と断定する書き方（`あり` なし）は使わない**。リモート可の案件があることを示し、全件フルリモートと誤認させないため。
- **末尾は必ず `エンジニア`** で締める。
- **〇〇 の部分**は、後述の「〇〇 に入る一覧」から **1 つだけ** 選ぶ（複数並べたり `／` `｜` で連結したりしない）。
- 全体で 30 字前後を維持。
- UPBUILD のエンジニア求人はこの書式で統一（Xedge はエンジニア求人を作らない）。
- **iRup のみ例外**: 2026-07-02 にユーザー指示で対人スキル訴求スタイル（`｜`区切りを含む）に切り替え済み。**2026-09-24〜、書式は `【未経験可】<具体言語>エンジニア｜<対人スキル訴求>` に統一**（`【未経験可】` を必ず先頭の `【】` に入れ、直後に職種名を置く。`【】` は 1 つだけ。ITコンサルタントと同一書式）。`<具体言語>` は本ページの「〇〇 に入る一覧」から選ぶ（Python/React/AWS 等。2026-09-14〜のルールを継続）。詳細は `companies/iRup/設定.md`「C 列（職種名）: iRup 専用の対人スキル訴求スタイル」を参照。
- **UPBUILD はテスト例外（2026-09-03〜）**: ユーザー指示で、東京・大阪・愛知（名古屋）全エリアの C 列を自由書式でテスト運用中。**2026-09-24〜、東京は `【未経験可】<具体言語>エンジニア<キャッチーな一言>｜フルリモート可`、大阪・愛知は `【<具体言語>エンジニア】<キャッチーな一言>｜フルリモート可` に統一**（大阪・愛知のみ `【】` の中身を `リモートあり`／`ポテンシャル採用` 等の条件タグから AWS／Azure／SOC／SIEM 等の**具体言語名＋エンジニア**に変更。東京は `【未経験可】` タグを維持し、言語名は 】の直後に置く。いずれも **`｜フルリモート可` を文末に必ず含める**。区切り記号は同日中に `・`→`｜` へ変更。UPBUILD 自由書式テスト運用に限り `｜` の使用を例外的に許可）。〇〇（具体言語名）は `クラウド`／`セキュリティ`のみの汎用語を使わない点は 2026-09-21 ルールを継続。**2026-09-28〜更新**: 東京は固定文字列 `【未経験可】クラウドエンジニア（フルリモートあり）`／`【未経験可】セキュリティエンジニア（フルリモートあり）`、大阪・愛知のクラウドは上記 09-24 書式（具体言語名）を継続、大阪・愛知のセキュリティは `【セキュリティエンジニア】<一言>｜フルリモート可`（言語名ではなく `セキュリティエンジニア`）。詳細・リスク・良い例は `companies/UPBUILD/設定.md`「C 列テスト運用: 自由書式」参照。（「2026-09-28 追加更新」が現行）
- **UPBUILD の経験者向け求人（大阪・名古屋の定番パターン）**: 実務経験を条件とする求人（大阪・名古屋の AWS／セキュリティ／ネットワーク構築案件など）は、冒頭タグに条件語を入れない。**2026-08-03〜のデフォルトは `【フルリモートあり】〇〇エンジニア`**（`未経験可`／`経験者採用`／`実務経験1年以上` 等の応募条件語を一切タイトルに含めず、`フルリモートあり` をそのままタグ化する）。実際の経験年数条件は AV 本文側（`■実務経験1年以上の方、歓迎` 等）にのみ明記する。
  - **背景（2026-08 UPBUILD パフォーマンス分析）**: 実掲載データで「(実務経験1年〜・フルリモート可)」等の条件羅列型タイトルは CTR 2.05〜2.47%（全社平均 6.28%・中央値 4.94% を大きく下回る）と判明。応募条件を職種名に書くと、クリック前に求職者が自己選別して離脱し露出機会を失うため、**経験者向け求人でも条件語はタイトルに出さない**方針に変更（2026-08-03 ユーザー指示）。旧パターン（`【実務経験1年以上】`→`【即戦力歓迎】`→`【経験者採用】` の順で条件語をタグ化する運用）は履歴として残すが、**新規作成では使わない**。
  - **同一勤務地内での重複回避**: 大阪・名古屋で同じ〇〇（例: セキュリティ×2）を使うと `【フルリモートあり】セキュリティエンジニア` のようにタイトル文字列が完全一致してしまう。以前は片方を近接する別ワード（`SOC`／`AWS` 等）に振って差別化していたが、**2026-08-06 ユーザー指示で UPBUILD の C 列 〇〇 は `クラウド`／`セキュリティ` の 2 語のみに限定**したため、この差別化手法は使わない。エリア間の差別化は E 列（勤務地名・地域訴求）で行う（詳細は `companies/UPBUILD/設定.md`「運用ルール」参照）。
  - **方針転換（2026-08-10 分析反映）→ 2026-08-11 巻き戻し**: 2026-08-10、2026-07-11〜08-09 の実データで経験者限定型（`実務経験1年〜` 等）の CTR が名古屋2.2〜2.8%と構造的に低いことが判明し、「名古屋・大阪でも未経験可＋強い訴求フレーズを優先」する方針に一時更新した。**しかし翌 2026-08-11 にユーザー指示で経験者向け（`【フルリモートあり】〇〇エンジニア`＋実務経験1年以上）に巻き戻し済み**。上記「2026-08-03〜のデフォルト」が現行仕様（データ上の CTR 劣位は変わらないが、ユーザーの事業判断による）。詳細は `companies/UPBUILD/設定.md`「追加分析」の巻き戻し注記を参照。
  - 詳細・前例は `companies/UPBUILD/設定.md`「名古屋・大阪混在の 5 件セット（定番パターン）」を参照。
- この書式は `.claude/列定義.md` の「C 列（職種名）の書式: 職種名のみ・簡潔で明確に」の **エンジニア向け具体化版**にあたり、エンジニア求人ではこちらが優先。

- `【未経験可】フルリモートありクラウドエンジニア`
- `【未経験可】フルリモートありセキュリティエンジニア`
- `【未経験可】フルリモートありデータベースエンジニア`
- `【未経験可】フルリモートありReactエンジニア`
- `【未経験可】フルリモートありAIエンジニア`（iRup 実績: CTR17.7%。2026-08-10 分析〔2026-07-11〜08-09〕では CTR14.1%・CVR10.6% で CTR/CVR とも高水準を再確認）
- `【未経験可】フルリモートありPythonエンジニア`（iRup 実績: 「Pythonデータサイエンティスト」系で CTR16.7%）

### 複数【】連結型（AI・データ系限定の例外・2026-08-10 追加）

`【未経験可】【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析` のように、`【】` タグを複数連結して属性を畳みかける型が iRup 実績で CTR21.3%（2026-08-10 分析・2026-07-11〜08-09）を記録した。UPBUILD でも同時期の分析で近似の型「【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析」が CTR14.5%（東京・港）を記録しており、**会社をまたいで有効性が確認された**（UPBUILD は C 列の 〇〇 が `クラウド`／`セキュリティ` の2語限定のため、UPBUILD ではこの型を E 列側で使う。詳細は `companies/UPBUILD/設定.md`「追加分析」参照）。上記「冒頭の `【未経験可】` と `フルリモートあり` は固定」「〇〇 は複数並べたり `／` `｜` で連結したりしない」という原則に対し、この型は **`／`／`｜` による同義語連結ではなく `【】` タグごとに別属性（未経験可／勤務形態／技術ワード／職種の細分類）を並べる**構成であり、原則には抵触しない。**AI・データ系（〇〇=`AI`／`データ`）に限り、この複数【】連結型を追加候補として使ってよい**。ただし通常の単一 〇〇 型より長くなるため、まず単一型（`【未経験可】フルリモートありAIエンジニア` 等）を基本とし、この型は変化を付けたいときの追加候補として使う。実際の掲載結果は `analyze-unlisted` スキルで確認すること。

**注意（2026-08-31 UPBUILD 実績で反面教師として確定）**: この型は CTR は高く出るが、応募につながらないリスクがある。UPBUILD の 2026-08-01〜08-31 実績で「【未経験可】【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析」が CTR19.6% にもかかわらず **CVR0%** だった（2026-08-10 時点では好例として紹介していたが、今回のデータで反面教師に確定。詳細は `本文スタイル.md`「AT/AU/AV とタイトルの整合」、`companies/UPBUILD/設定.md`「追加分析（2026-08-31）」参照）。この型を使う場合は、AT・AU 側で具体タスク・報酬の透明性など応募判断材料を必ず厚く書き、タイトルで作った期待と本文の中身にギャップを作らないこと。

**注意（2026-08-31 iRup 実績でも相対的な弱さを再確認）**: iRup の 2026-08-01〜08-31 実績（コンサル＋エンジニア95件）でも、「【未経験可】【フルリモートあり】【AI】【データサイエンティスト】データエンジニア・データ分析」が CTR11.2%・**応募0** と、同期間の最上位（「外国籍｜クラウドエンジニア」CTR19.3%・CVR20.9% 等）に比べ明確に見劣りした。単一〇〇型や属性限定型（後述）の方が名指しが明確でパフォーマンスが安定する傾向にあるため、複数【】連結型は引き続き**基本ではなく追加候補**の位置づけとし、多用しない（詳細は `companies/iRup/設定.md`「パフォーマンス実績の更新（2026-08-31）」参照）。

### 悪い例（Indeed に弾かれる／旧書式）

- `【未経験可】フルリモートありインフラ／保守運用エンジニア`（〇〇 に `／` を含む・職種名内に複数領域）

## D 列「職業カテゴリー」の有効値（Indeed 一括アップロード）

D 列は **Indeed の職業カテゴリーの「リーフ名」完全一致のみ**受け付ける（一括アップロード検証で弾かれる）。複数指定は `、` 区切り。エンジニア求人で使える **IT カテゴリーの有効リーフ**は以下（2026-05 時点、`/bulkupload/occupation-reference` で確認）:

- `システムエンジニア` は **親グループでリーフではない**ため D 列に書くと弾かれる（`web/オープンSE` 等のリーフを使う）。`プログラマー` も同様に親グループ。

| 有効リーフ（D 列にそのまま書ける） |
| --- |
| `フロントエンドエンジニア` |
| `サーバーサイドエンジニア` |
| `データベースエンジニア` |
| `ネットワークエンジニア` |
| `セキュリティエンジニア` |
| `データエンジニア` |
| `DevOpsエンジニア` |
| `QA/テストエンジニア`（「QAエンジニア」「テストエンジニア」単独は不可。この1語で表す） |
| `保守/運用/サポートエンジニア` |
| `社内システムエンジニア` |
| `SRE（Site Reliability Engineer）` |
| `アーキテクト` |
| `データサイエンティスト` / `データアナリスト` |

**弾かれた実績（使わない → 置換）**:
- `インフラエンジニア` → `DevOpsエンジニア` または `ネットワークエンジニア`／`サーバーサイドエンジニア`
- `アプリケーションエンジニア` → `サーバーサイドエンジニア`
- `QAエンジニア`・`テストエンジニア` → `QA/テストエンジニア`
- `システムエンジニア`（親グループ）→ `サーバーサイドエンジニア` 等のリーフ

C 列で選んだ〇〇 に応じた D 列の目安: AWS/クラウド/インフラ→`サーバーサイドエンジニア、ネットワークエンジニア、DevOpsエンジニア`／セキュリティ→`セキュリティエンジニア、ネットワークエンジニア`／DB・データ基盤→`データベースエンジニア、データエンジニア`／言語FW（Python/Go 等）→`サーバーサイドエンジニア、データベースエンジニア`／QA→`QA/テストエンジニア、サーバーサイドエンジニア`。

## 運用ルール

- C 列の生成時、**まず本ドキュメントの〇〇一覧から 1 つ選ぶ**。リスト外のワードを使いたい場合は、本ドキュメントに追記してから使う（その場限りで増やさない）。
- 複数件まとめて生成するときは、**できるだけ別のカテゴリー・別のワードを散らす**（10 件全部 `AWS` などにしない）。
- **パフォーマンス実績（UPBUILD 2026-06-12〜07-11 分析、CTR 基準）**: 東京（港区・台東区）で `データ`／`React`・`TypeScript` 等のフロントエンド系／`AWS`／`セキュリティ` は CTR が高い（例: データエンジニア港区 19.6%、React フロントエンド港区 15.0%、AWS インフラ台東区 11.6%）。件数配分に迷ったら、東京 hub ではこれらのカテゴリーを優先候補にする。
- **パフォーマンス実績（iRup 2026-06-12〜07-11 分析、CTR/CVR 基準）**: 先頭に具体職種＋希少キーワード（`AI`／`データ`／`Python` 等）＋「フルリモートあり」を置く構成は CTR・応募率とも高い（例: データエンジニア・データ分析系 CTR22.2%、フルリモートありAIエンジニア CTR17.7%、Pythonデータサイエンティスト系 CTR16.7%）。逆に、**キャリアチェンジのストーリーや情緒コピーを職種名より前に置く構成（`｜` 区切りの物語型）は CTR が著しく低い**（最下位は CTR1.0%）。iRup の C 列例外スタイル（`companies/iRup/設定.md`）を使う場合は、職種名・技術ワードを先頭寄りに置く／このパターンの使用頻度を下げることを優先する（詳細・優先順位は `companies/iRup/設定.md`「パフォーマンス実績に基づく優先順位」参照）。
- **パフォーマンス実績（iRup 2026-07-04〜08-02 分析・エンジニア＋ITコンサル87件、CTR 基準）**: 上記の傾向を再確認・強化。`データサイエンティスト`／`データエンジニア` 系タイトルが CTR24.08%、`AIエンジニア` が CTR16.08% と全体平均（CTR11.00%）を大きく上回り、依然として `AI`／`データ` が最強の 〇〇 候補。逆に低かったのは、業界名や更改対象システム名まで職種名に詰め込んだ**長く専門的すぎる基盤系タイトル**（例: 銀行系基盤更改エンジニア（Linux）CTR0.42%）。〇〇 は一覧語 1 つに絞り、業界・案件名・更改対象などの修飾語を C 列に足さない（詳細は `briefs/エンジニア.md`「E キャッチコピー」参照）。
- **地方×細分化職種の同一タイトル量産は避ける**: 名古屋（中村区）で `SOC`／`QA`／`コンテナ`・`クラウド` 等の細分化ワードを、同一勤務地でタイトルが実質同じまま複数件・複数回にわたって重ねて掲載すると CTR が著しく落ちる（実績: SOC エンジニア名古屋 0.9%、QA エンジニア名古屋 2.8〜3.7%×3 件、コンテナ/クラウドエンジニア名古屋 4.0〜4.8%）。地方向けは、①同一〇〇×同一勤務地の組み合わせを直近の掲載一覧と照らして重複させない、②件数を絞る、③E 列キャッチコピーで訴求を変えて差別化する、を優先する。
- **パフォーマンス実績（UPBUILD 2026-07-04〜08-02 分析、クラウド／セキュリティ限定 40 件）**: 上記の地方量産傾向はエリア単位でも再確認された（東京 CTR8.47%＞大阪 CTR4.33%＞愛知(名古屋) CTR3.12%）。愛知（名古屋）は特に埋没しやすいため、E 列で地域名や訴求を差し込んで差別化する（詳細・具体的な良い例/悪い例・CVR 仮説は `companies/UPBUILD/設定.md`「エリア別パフォーマンス傾向と改善ルール」参照）。
- AT／AU 本文では「技術スタック早見表」のサブ領域を素材として組み合わせる。C 列のワードと AT 本文のテーマが整合すること（例: C 列が `セキュリティ` なら AT 本文も SOC／SIEM／脆弱性診断などセキュリティ寄りに）。
