# 非掲載求人の理由分析（共通スキル）

Indeed の採用企業管理画面で **「非掲載」になった求人がなぜ非掲載なのか**を、Playwright MCP でブラウザを実操作して突き止め、原因と修正方針を報告するスキル。求人の新規作成は `draft-jobs`、一括アップロードは `/upload-indeed` が担当。本スキルは **読み取り・分析が主目的**で、求人の編集や有料掲載の操作は勝手に行わない（必要なら最後にユーザーへ提案）。

## 関連ドキュメント

| 用途 | ファイル |
| --- | --- |
| 列の分類・入力規則・全固定ルール（C 列・AD・タグ・M/N/W/BA 等） | `.claude/列定義.md` |
| エンジニア C 列固定書式・D 列有効カテゴリー | `.claude/エンジニア専門領域.md` |
| 本文スタイル（AT 仕事内容ほか） | `.claude/本文スタイル.md` |
| 会社固有値（社名・BD/BM 等） | `.claude/companies/<会社>/設定.md` |
| 一括アップロード手順（ログイン・会社切替の流儀を共有） | `.claude/commands/upload-indeed.md` |

## 事前条件

- プロジェクトルートに `.env` があり `INDEED_EMAIL` / `INDEED_PASSWORD` が定義されていること（`/upload-indeed` と共通。**コミット禁止**）。
- Playwright MCP（`mcp__playwright__*`）が接続されていること。
- 1 アカウントで 3 社（iRup / UPBUILD / Xedge）を保持。会社は右上のドロップダウンで切り替える。
- 修正方針の提示には、対象会社の最新 xlsx（`<会社>/<会社>_YYYYMMDD.xlsx`）が手元にあると該当行を指摘できる（なくても理由分析は可能）。

## ワークフロー

### ステップ 0: 会社・対象期間を確認（最初に必ず）

対象会社（iRup / UPBUILD / Xedge）を確認する。引数で渡っていればそれを使う。複数社を見たい場合は会社ごとに繰り返す。

**対象期間（定期実行前提）**: このスキルは定期実行を想定しているため、**対象は「実行日から過去 1 ヶ月以内」に掲載/作成された求人に限定**する（求人一覧の「掲載日」列で判定。例: 実行日 2026-06-05 なら 2026-05-05 以降）。
- 理由: ①直近に作った（draft-jobs の最新成果物）求人の品質を回すのが目的。②それ以前のレガシー求人は「掲載期間終了」が多く現行ワークフロー対象外なので、期間で切ると自然に除外できてノイズが減る。
- 1 ヶ月より前のものは集計の対象外として件数だけ「対象外 N 件（掲載日 1 ヶ月超）」と明記し、深掘りしない。ユーザーが「全期間で見たい」と言えば期間を外す。

### ステップ 1: ログイン

1. `https://secure.indeed.com/auth?continue=https%3A%2F%2Femployers.indeed.com%2Fbulkupload&hl=ja&co=JP&userType=employer` にアクセス。
2. 既にログイン済みなら次へ。未ログインなら `.env` のメール→パスワードでログイン。
3. **2 段階認証が出たら停止してユーザーに通知**（自動で進めない）。

### ステップ 2: 会社を切り替える

1. 画面右上の会社名表示エリア（現在のアクティブ会社）をクリック。
2. ドロップダウンから対象会社を選択（部分一致で可。例: `iRup` →「株式会社iRup」、`Xedge` →「株式会社Ｘｅｄｇｅ」）。
3. 切替後、右上の表示が対象社名になっているか必ず確認。違えばエラー終了。

### ステップ 3: 求人一覧で「非掲載」＋「掲載中（募集中）」を抽出（比較用に両方）

1. `https://employers.indeed.com/jobs` にアクセス。
2. 各求人行の **「ステータス」列**は combobox で、値が **`募集中`（掲載中）/ `非掲載` / `休止中`** のいずれか。後段の比較（ステップ 5）のため、**`非掲載` と `募集中` の両方を「掲載日」「職種名（C列）」つきで集める**。
   - 上部の **「ステータス」フィルター**で絞り込める場合は使うと速い。フィルターに依存せず **全行のステータス列を走査**しても良い（`非掲載` は `募集中` と同じ一覧に混在して出る）。
   - **対象期間で絞る（ステップ 0）**: 「掲載日」列が **実行日から過去 1 ヶ月以内**の行だけを対象にする。1 ヶ月超の行は件数だけ数えて「対象外」とし、確認事項の深掘りはしない。
   - 件数が多い（一覧はページネーションあり・例: 185 件）。**ページ送りして全件のステータス列を走査**するか、フィルターで絞る。取りこぼしたら「N 件中 M 件を確認」と必ず明記する（黙って打ち切らない）。
   - 効率化: スナップショットが巨大なので、`browser_evaluate` で各行の「職種名(C列)・ステータス・勤務地・掲載日・確認事項件数(N件)」を一括スクレイプし、ページ送りしながら配列に貯めると速い（実操作で確認済みの手法）。
3. `非掲載` の行のすぐ下には展開ブロックがあり、見出し **「求人は非掲載です」**＋本文 **「この求人を Indeed PLUS に掲載するには、有料掲載してください。(N件の確認事項)」**＋ボタン **「詳細を確認」「有料掲載する」** が出る。
   - ⚠️ **このリスト上の「有料掲載してください」は Indeed の有料掲載（PLUS）への誘導文で、真の非掲載理由ではないことがある。**「(N件の確認事項)」が審査上の指摘件数。**真の理由は必ず次ステップの「詳細を確認」ダイアログで取る。**

### ステップ 4: 「詳細を確認」で非掲載理由（確認事項）を原文取得

各 `非掲載` 求人について:

1. その行の **「詳細を確認」** ボタンをクリック。
2. **「詳細を確認」ダイアログ**が開き、`確認事項` が文章で表示される。**この文言を一字一句そのまま（原文で）記録する**。
   - 実例（2026-06 時点・出版デザイナー求人）:
     > 職種名: 職種名が不明確、または職種名以外の求人内容に記載すべき情報（仕事内容、雇用形態など）が含まれている可能性があります。職種名は簡潔で明確なものに修正してください。
   - ダイアログには「求人を編集した場合、編集内容が反映されるまで数時間かかる場合があります。」の注記と、**「閉じる」「編集する」** ボタンがある。
3. 読み取ったら **「閉じる」** で閉じ、次の求人へ。**「編集する」「有料掲載する」は押さない**（ユーザー確認なしに求人を変更しない）。

> 操作のコツ（Playwright）: 要素の `ref` はスナップショットを取り直すたびに変わる。**「snapshot →（同じ snapshot の ref で）click」を 1 セットで行う**。スナップショットが巨大なときは `filename` 付きで保存し、`grep`/`Read`（offset/limit）または subagent で必要箇所だけ読む。`非掲載` の行が見つからないときは画面を上端へスクロール／ページ送りしてから再取得する。

### ステップ 5: 掲載中（募集中）求人との比較 ― 許容ラインを特定（重要）

「C 列に仕事内容・待遇・記号が入る＝即アウト」では**粗すぎる**。実際には **掲載が通る語/形式**と**弾かれる語/形式**の線引きがある。**非掲載と掲載中（募集中）の C 列を突き合わせて、その境界（許容ライン）を実データから特定する**。

手順:
1. ステップ 3 で集めた **非掲載の C 列**群と **募集中の C 列**群を並べる（同じ職種・同じ対象期間で）。
2. C 列を「**接頭タグ `【…】`**」「**職種名本体**」「**付加語（リモート/待遇/キャッチ/記号）**」に分解し、**どの語・形式が募集中に多く・非掲載に多いか**を対比する。
3. 「掲載実績のある語/形式（＝採用してよい）」と「非掲載に偏る語/形式（＝避ける）」を表にまとめる。

**実データで確認済みの許容ライン（2026-06 Xedge。新パターンが出たら更新）**:

| 観点 | 掲載が通る（採用してよい） | 弾かれやすい（避ける） |
| --- | --- | --- |
| 接頭タグ | **`【未経験可】`** | **`【未経験OK】`**（同義でも非掲載に偏る。`可`に統一） |
| リモート表現 | **`フルリモートあり`**（エンジニア固定書式に含まれ掲載実績あり） | （過度な条件の羅列） |
| 職種名本体 | 簡潔な職種名（例: `出版デザイナー`/`SNSマーケター`/`Webデザイナー`/`動画クリエイター`/`〇〇エンジニア`） | 職種名が埋もれる長文 |
| 付加語 | 上記の許容語の範囲で最小限 | 仕事内容（「企画から学べる」）・待遇（「賞与年4回」「推し活手当」）・キャッチ（「プロへ」「一気通貫」）・記号（`／` `｜` `（）` `※` `！`）・カッコ内技術列挙（`（AI・DX・…）`） |

> 注: 接頭タグの `可`/`OK` のような差は**実データの相関**であって Indeed 公式の明文基準ではない。**毎回この比較で再確認**し、サンプルが少なければ「仮説」と明記する。

### ステップ 6: 原因の分類と修正方針（SSoT と突き合わせ）

確認事項の原文を、当プロジェクトのルールと既知パターンに照合して **推定原因＋具体的な修正方針**を出す。代表パターン:

| 確認事項（Indeed の文言・抜粋） | 推定原因 | 修正方針（SSoT 参照） |
| --- | --- | --- |
| 「職種名: …職種名が不明確、または職種名以外の…情報（仕事内容、雇用形態など）が含まれている…」 | **C 列（職種名）に訴求・仕事内容・待遇が混入** | ステップ 5 の許容ラインに寄せる。`【未経験可】<職種名>`（`OK`でなく`可`）、エンジニアは `【未経験可】フルリモートあり〇〇エンジニア`。仕事内容/待遇/キャッチ/記号は外し E 列・本文へ。→ `列定義.md`「C 列（職種名）の書式」／`エンジニア専門領域.md` |
| 「Indeed PLUS に掲載するには有料掲載してください」だけで確認事項が実質ない | 審査上の問題ではなく**有料掲載（PLUS）枠の話**の可能性 | 無料掲載運用なら基本そのまま（iRup は無料掲載枠）。掲載強化が必要かをユーザーに確認 |
| 給与・試用期間・タグ等の値が不正 という趣旨 | M/N/W/BA・AD（`か月`）・BE/BF/BG 許容値・BR 空欄などの違反 | → `列定義.md` の該当固定ルール／関連メモリ |
| 本文・社名に関する指摘 | 本文スタイル・社名表記 | → `本文スタイル.md`（AT は具体・散文型 300 字／社名は各社の自社名） |
| 「固定残業代の最低賃金: 固定残業代が地域別最低賃金を下回っている可能性…」／「試用期間中の固定残業代: …地域別最低賃金を下回っている…」 | **固定残業代（P=あり）の額が地域別最低賃金未満**。試用期間（AE 同条件でない場合）も同様 | 固定残業代を使うなら**地域別最低賃金以上**に。現行テンプレは P列＝`なし` 既定なので新規では再発しない。→ `列定義.md` P/Q〜V・AE/AF〜AS（2026-06 Xedge レガシー求人で確認） |
| 「年齢に関する文言: …年齢に基づく差別・優先採用…」／「国籍や出身地に関する差別的な表現: …」 | **本文・条件に年齢/国籍の制限・差別的表現**が混入 | 年齢層の指定・年齢/国籍による制限表現を除去（厚労省の例外事由を使う場合も適切に）。→ `本文スタイル.md`・`列定義.md`（2026-06 Xedge レガシー求人で確認） |
| 「この求人は掲載期間が終了しています。現在も求人を行っている場合、…有料掲載が必要です。」 | **審査エラーではなく掲載期間切れ**（古い求人）。複数確認事項の1つとして併記されることが多い | 現在も募集なら再投稿／有料掲載。旧運用の遺物なら整理（クローズ）。他の確認事項（C列・固定残業代等）と切り分ける |

> **新しい文言が出たら、その原文と対処をこの表に追記する**（このスキルを SSoT として育てる）。当てはまるルールが無ければ「Indeed 既知ルール外。要ユーザー判断」と明記する。

**方針: 許される範囲でギリギリを攻める（最小化ではなく最大訴求）**
- C 列の修正方針は「とにかく削って職種名だけにする」ではない。**掲載が通る範囲で訴求語をできるだけ残す**のが狙い。
- ステップ 5 で**掲載実績が確認できた語/形式は積極的に採用**してよい。とくに **`【未経験可】`** と **`フルリモートあり`** はタイトルに入れたい語として優先的に残す（掲載実績あり）。
- 修正方針を書くときは「これを全部消す」ではなく「**掲載実績のある語に寄せつつ、訴求をギリギリまで残した C 列案**」を 1 つ具体的に提示する（例: `【未経験OK】自社案件で企画から学べる動画クリエイター` → `【未経験可】動画クリエイター`、エンジニアなら `【未経験可】フルリモートありAIエンジニア`）。
- ただし攻めて非掲載になっては本末転倒。比較で根拠の薄い語は「仮説・要観察」とし、次回の定期実行で掲載/非掲載の結果を見て許容ラインを更新する（攻めた語が落ちたら一段下げる）。

可能なら、対象会社の最新 xlsx（`<会社>/<会社>_YYYYMMDD.xlsx`）を開き、**非掲載求人に対応する行・列（例: C 列）**を特定して「この行のここを直す」と具体的に示す。

### ステップ 7: レポート出力＋ログ保存

1. チャットに**求人ごとのサマリ表**を提示:
   - 会社／職種名（C 列）／勤務地／掲載日／ステータス／**確認事項（原文）**／推定原因／推奨修正（許容ラインに寄せた C 列案）／該当 xlsx 行（分かれば）。
   - **許容ライン表**（ステップ 5 の比較結果。掲載が通る語/形式 ・ 避ける語/形式）。
   - 全体所感（例: 「非掲載 M 件中 L 件が C 列の職種名エラー。`【未経験OK】`→`【未経験可】`化と訴求語の整理で再生成・再アップロードが必要」）。
   - **対象期間と件数**を明記（「<会社> の対象期間 YYYY-MM-DD〜 / 全 N 件中 M 件を確認、うち非掲載 K 件、対象外（1 ヶ月超）J 件」）。
