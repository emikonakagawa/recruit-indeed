# 掲載求人のパフォーマンス分析（共通スキル）

Indeed 採用企業管理画面のアナリティクスから、掲載中求人の **表示回数・クリック数・応募数**を取得し、**タイトル（C 列・E 列）と求人内容（AT/AU/AV）の良し悪し**を数値で評価する。求人作成は `draft-jobs`、非掲載理由の分析は `analyze-unlisted` が担当。本スキルは **読み取り・分析が主目的**で、求人の編集や有料掲載は勝手に行わない。

## 指標の考え方（このスキルの核）

| 指標 | 計算式 | 何がわかるか |
| --- | --- | --- |
| **CTR（クリック率）** | クリック数 ÷ 表示回数 | **タイトルの良さ**（C 列職種名・E 列キャッチコピー）。表示されたうちどれだけ「見たい」と思われたか |
| **応募率（CVR）** | 応募数 ÷ クリック数 | **求人内容の魅力**（AT/AU/AV・給与/条件）。開いたうちどれだけ「応募したい」と思われたか |
| （補助）応募開始率 | 応募開始数 ÷ クリック数 | 内容を見て応募に進んだ割合 |
| （補助）応募完了率 | 応募数 ÷ 応募開始数 | 応募フォームの離脱の少なさ |

→ **CTR が高い＝タイトルが良い**／**CVR が高い＝内容が魅力的**。低い側は改善対象。

## 関連ドキュメント

| 用途 | ファイル |
| --- | --- |
| C 列（職種名）・E 列・全列ルール | `.claude/列定義.md` |
| 本文スタイル（AT 仕事内容＝具体散文 300 字／AU/AV） | `.claude/本文スタイル.md` |
| エンジニア C 列固定書式・技術スタック | `.claude/エンジニア専門領域.md` |
| 職種別ブリーフ（何を伝えるか） | `.claude/briefs/<職種>.md` |
| ログイン・会社切替の流儀（共通） | `.claude/commands/upload-indeed.md` |

## 事前条件

- `.env` に `INDEED_EMAIL` / `INDEED_PASSWORD`（`/upload-indeed` と共通。**コミット禁止**）。
- Playwright MCP（`mcp__playwright__*`）が接続されていること。
- 1 アカウントで 3 社を保持。会社は右上ドロップダウンで切替。

## ワークフロー

### ステップ 0: 会社・期間を確認

- 対象会社（iRup / UPBUILD / Xedge）を確認（引数があればそれを使う）。
- 分析期間を確認。**既定は直近 30 日**（アナリティクスの既定値）。必要なら任意期間。

### ステップ 1: ログイン → ステップ 2: 会社切替

`upload-indeed.md` と同じ。
1. `https://secure.indeed.com/auth?continue=https%3A%2F%2Femployers.indeed.com%2Fbulkupload&hl=ja&co=JP&userType=employer` でログイン（2 段階認証が出たら停止して通知）。
2. 右上の会社名をクリックし対象会社を選択。右上表示で切替を確認。

### ステップ 3: アナリティクス（求人別）を開く

1. `https://employers.indeed.com/analytics/report-jobs-campaigns` にアクセス。
2. **「Indeed アナリティクスのご紹介」ツアーのダイアログが出たら「閉じる」で閉じる**。
3. 期間（画面右上の日付レンジ）を必要に応じて設定。表示中の期間（例:「2026年5月6日～2026年6月5日のデータを表示」）を控える。
4. テーブル上部のトグル **「キャンペーン / 求人」で「求人」を選ぶ**（求人別の行になる）。
5. トラフィック種別の絞り込みがある場合は **「合計」**（オーガニック＋スポンサー）にする。無料掲載運用なので合計で見る。

### ステップ 4: 求人別テーブルを取得

求人別ビューのテーブル列（確認済み）:

| 求人（職種名＋勤務地） | キャンペーン | 表示回数 | クリック数 | 応募開始数 | 応募数 | 費用 |
| --- | --- | --- | --- | --- | --- | --- |

- 先頭に **合計行**（例:「合計：43行 / 表示回数 15,664 / クリック数 1,577 / 応募開始数 87 / 応募数 66 / 費用 ¥13,000」）。
- **全行を取得**する。方法は次のいずれか:
  - **エクスポート**（テーブル右上の「エクスポート」ボタン）で CSV を取得して読む（行数が多い・確実）。ダウンロード先を控える。
  - または画面のテーブルを **ページ送りしながらスナップショットで読む**（巨大スナップショットは `filename` 付き保存 →`grep`/`Read`/subagent で必要箇所だけ）。
- 取りこぼしたら「合計 N 行中 M 行を取得」と必ず明記（黙って打ち切らない）。
- 注意: アナリティクスに出るのは **期間内にトラフィックがあった求人**が中心で、全求人数（求人一覧の総数）とは一致しないことがある。差分があれば明記する。

> 補足: 個別求人の数値は、求人詳細ページ `…/jobs/view?employerJobId=…` の **「パフォーマンスの概要」**（表示回数／クリック数／応募数）でも確認できる。1 件だけ深掘りするときの裏取りに使う。

### ステップ 5: 計算・ベンチマーク・集計

各求人について算出:
- **CTR = クリック数 ÷ 表示回数**
- **応募率(CVR) = 応募数 ÷ クリック数**
- （補助）応募開始率・応募完了率

サンプル数ガード（小さい数字は誤判定するため）:
- **CTR は 表示回数 ≥ 100 の求人のみ評価**（未満は「データ不足」と明記）。
- **CVR は クリック数 ≥ 20 の求人のみ評価**（未満は「データ不足」）。
- 個別求人だけで断定せず、**職種ごと（・勤務地ごと）に集計**して傾向を見る。

ベンチマーク:
- 全体（その会社・期間）の **CTR と CVR の中央値・平均**を出し、各求人・各職種をそれと比較して「高い/低い」を相対判定。
- **高 CTR 上位／低 CTR 下位**、**高 CVR 上位／低 CVR 下位**を抽出し、それぞれの C 列タイトル・E 列・本文の特徴（共通点）を言語化する。

### ステップ 6: レポート出力（`分析レポート/`）

- 保存先・命名は `分析レポート/README.md` の規則に従う。**日本語タイトル＋日付**。
  - ファイル名: `分析レポート/掲載求人パフォーマンス分析_<会社>_YYYYMMDD.md`（同日複数回は末尾 `_2` 等）。
  - スクショも同フォルダに対応名で保存可。
- レポート本文の構成:

  ```
  # 掲載求人パフォーマンス分析 ― <会社>（対象期間 YYYY-MM-DD〜YYYY-MM-DD）

  ## サマリ
  - 取得: 合計 N 行中 M 行 / 全体 CTR=◯◯% / 全体 CVR=◯◯%
  - 所感: タイトル（CTR）と内容（CVR）の総評

  ## 求人別メトリクス（CTR・CVR 付き）
  | 職種 | 職種名(C列) | 勤務地 | 表示回数 | クリック | 応募開始 | 応募 | CTR | CVR | 判定 |
  |---|---|---|---|---|---|---|---|---|---|
  | … |

  ## タイトルの良し悪し（CTR 分析）
  - 高 CTR の共通点: …（例: 〇〇 を含むタイトルが強い）
  - 低 CTR の共通点: …
  ## 内容の良し悪し（CVR 分析）
  - 高 CVR の共通点: …（例: AT が具体・条件が明確）
  - 低 CVR の共通点: …
  ## 職種別の傾向
  - …

  ## ドキュメント改善プロンプト（次の改善作業用）
  （↓ ステップ 7 のプロンプトをそのまま貼る）
  ```

### ステップ 7: ドキュメント修正方針プロンプトを生成（重要な成果物）

レポート末尾に、**別の AI セッション（または次の自分）にそのまま渡せるプロンプト**を、今回のデータを埋め込んで生成する。目的は「以降、質の良い求人を作れるよう SSoT ドキュメントを更新させる」こと。雛形:

```
あなたは Indeed 求人作成ワークスペースのドキュメント整備担当です。
以下は実掲載データに基づくパフォーマンス分析の結果です。これを踏まえ、今後より高い CTR（タイトル）と応募率（内容）を得られるよう、SSoT ドキュメントを更新してください。

# 対象ドキュメント（必要箇所のみ・SSoT を壊さない）
- タイトル指針: `.claude/列定義.md`「C 列（職種名）の書式」／`.claude/エンジニア専門領域.md`／各 `briefs/<職種>.md` の C 列・E 列例
- 内容指針: `.claude/本文スタイル.md`「AT 仕事内容」ほか／各 `briefs/<職種>.md` の AT/AU/AV の核

# データ（今回の分析結果）
- 対象会社 / 期間: <会社> / <期間>
- 全体: CTR=<x>% 応募率=<y>%（中央値: CTR=<>%, CVR=<>%）
- 高 CTR 求人（タイトルが効いた）: <職種名と CTR を列挙＋共通点>
- 低 CTR 求人（タイトル要改善）: <列挙＋共通点>
- 高 CVR 求人（内容が魅力的）: <職種名と CVR を列挙＋共通点>
- 低 CVR 求人（内容要改善）: <列挙＋共通点>
- 職種別傾向: <Webデザイン/マーケ/動画/出版/エンジニアごとに一言>

# 指示
1. 上記の「効いた要素」を、該当ドキュメントのガイドライン・良い例として**具体的に追記/修正**する（抽象論にしない。実際に伸びた表現を例示）。
2. 「効かなかった要素」を悪い例・避ける指針として明記する。
3. C 列（タイトル）の Indeed 審査制約（職種名のみ・簡潔）を壊さない範囲で、CTR を上げる工夫（E 列キャッチコピーや表記）を提案・反映する。
4. 変更は最小限で重複定義を作らない（SSoT を 1 箇所に保つ）。サンプル数が少ない指標は「仮説」と明記し、断定しない。
5. 変更後、何をどの根拠（どの求人データ）で変えたかを箇条書きで報告する。
```

> 数値・職種名・共通点は **実データで具体的に埋める**。プレースホルダのまま出力しない。

## 注意

- `.env` は絶対にコミットしない。2 段階認証・想定外画面が出たら停止して通知。
- 数字が小さい期間は結論を急がない（「データ不足」「仮説」と明記）。
- UI 文言・列名・トグルは変わりうる。挙動が変わったら本ファイルを更新する（SSoT として保守）。
- 一時取得した CSV やスナップショットの巨大ファイルはレポート確定後に整理する（`.playwright-mcp/` は gitignore 済み）。
